# Terraform Questions
<details><summary>01. What is Terraform?</summary><br><b>

  - Terraform is an open-source Infrastructure as Code (IaC) tool developed by HashiCorp that is used to define, provision, and manage infrastructure in a declarative way.
- Using Terraform, we write infrastructure configurations in HCL (HashiCorp Configuration Language), and Terraform automatically creates, updates, or deletes cloud and on-prem resources to match the desired state.
- Terraform enables teams to manage infrastructure reliably and consistently by treating infrastructure as code.
- Terraform is cloud-agnostic and supports multiple providers like AWS, Azure, GCP, Kubernetes, etc.
- It follows a declarative approach, where we define what infrastructure we want, not how to create it.
- Terraform uses a state file to track the current state of infrastructure.
- It supports versioning, reuse, and automation through modules and variables.
- Commands like terraform plan and terraform apply help preview and safely apply infrastructure changes.
</b></details>
<details><summary>02. What is Terraform Init?</summary><br><b>

  **Terraform init** - It initializes a working directory and installs providers defined in the terraform configuration file.

```bash
terraform init
```

When we execute the above command then the below hidden folder and file will be generated by terraform.
- .terraform folder - Installed provider files are stored in this folder.
- .terraform.lock.hcl - This file keeps a track of which provider is installed and which version we have.

</b></details>
<details><summary>03. What is Terraform Plan?</summary><br><b>

  **Terraform Plan** - terraform plan performs a dry run by comparing the desired configuration with the current state and shows the actions Terraform will take without modifying infrastructure.

- It helps us to find the difference between current and desired or configured state.
-  It shows what Terraform will change before it actually makes any changes.
 

```bash
terraform plan
```

When we execute the above command then the below things will happen.
- Reads Terraform configuration files (.tf).
- Loads current state file.
- Compares desired state vs actual state.
- Generates a change plan.
</b></details>
<details><summary>04. What is Terraform Apply?</summary><br><b>

  **Terraform apply** - Terraform apply executes the execution plan and brings the infrastructure to the desired state by making actual changes.

- terraform apply is used to create, update, or destroy infrastructure by executing the changes defined in the Terraform execution plan.
- It applies the desired configuration to reach the target state.
- It makes real changes to the infrastructure.
- It uses the execution plan to ensure controlled and predictable deployments.
 

```bash
terraform apply

## providing confirmation in command only.
terraform apply -auto-approve
```

When we execute the above command then the below things will happen.
- Reads Terraform configuration files (.tf).
- Loads the current state file.
- Generates an execution plan (if not provided).
- Prompts for user confirmation (yes).
- Creates, updates, or deletes resources as required.
- Updates the state file after successful execution.

  ## Best Practice
  ```bash
  terraform plan -out=tfplan
  terraform apply tfplan
  ```
  - Ensures the applied changes are exactly what was reviewed.
  - Commonly used in production and CI/CD pipelines.
</b></details>
<details><summary>04.  What is Terraform Destroy?</summary><br><b>

  **Terraform destroy** - Terraform destroy removes all infrastructure managed by Terraform by executing a destroy plan and updating the state accordingly.

- terraform destroy is used to delete all infrastructure resources that are managed by Terraform for a given configuration.
- It removes infrastructure created by Terraform.
- It is commonly used for cleanup, testing, and cost control.
- It permanently deletes resources, so it must be used carefully.
 

```bash
terraform destroy

## delete a specific thing.
terraform destroy -target resouretype.resourcename
```

When we execute the above command then the below things will happen.
- Reads Terraform configuration files (.tf).
- Loads the current state file.
- Generates a destroy execution plan (if not provided).
- Prompts for user confirmation (yes).
- Deletes all managed resources.
- Updates the state file after successful destruction.

  ## Best Practice
  ```bash
  terraform destroy -auto-approve
  ```
  - Used mainly in automation or CI/CD pipelines.
  - Avoid using in production without proper approvals.
</b></details>
<details><summary>05.  What is Terraform State?</summary><br><b>

  **Terraform State** - Terraform state is a json file that tracks and maps real infrastructure resources to Terraform configurations, enabling accurate planning and management of infrastructure.

- Terraform state is a file that keeps track of the real infrastructure resources that Terraform manages and maps them to the configuration defined in .tf files.
- It stores the state about your real world resources of your managed infrastructure.
- It acts as the source of truth for Terraform.
- It helps Terraform understand what resources already exist.
- It enables Terraform to calculate accurate execution plans.
 
The state file is usually named:
```bash
terraform.tfstate
terraform.tfstate.backup -It is the previous state of the resources.
```

When Terraform uses the state file, the below things happen.
- Stores information about created resources.
- Maps resource IDs to Terraform resource blocks.
- Tracks dependencies between resources.
- Detects changes between actual and desired infrastructure.
- Enables safe updates and deletions.

  ## Best Practice
  -  Use remote state with locking (e.g., S3 + DynamoDB).
  -  Never manually edit the state file.
  -  Secure state files as they may contain sensitive data.
  
| Local State             | Remote State                             |
| ----------------------- | ---------------------------------------- |
| Stored on local machine | Stored in backend (S3, Azure Blob, etc.) |
| Not safe for teams      | Safe for collaboration                   |
| No locking              | Supports state locking                   |

## Terraform State Commands
```bash
# Lists all resources tracked in the state.
terraform state list

# Shows detailed state information for a specific resource.
terraform state show <resource>

# Removes a resource from state without deleting the actual infrastructure.
terraform state rm <resource>

# Moves or renames resources within the state.
terraform state mv <source> <destination>
```
</b></details>

<details><summary>10. What is a Variable?</summary><br><b>

  - **Terraform variables** are input parameters that allow infrastructure code to be flexible, reusable, and environment-independent.
- Terraform Variables are used to parameterize configurations, allowing you to pass values into Terraform so the same code can be reused across environments (dev, test, prod).
- Variables make Terraform code dynamic and reusable.
- They help avoid hard-coding values
- Values can be overridden without changing the code

 ## Variable Block Syntax:
 ```bash
variable "instance_type" {
  description = "EC2 instance type"
  type        = string
  default     = "t2.micro"
}
```

## Parts of a Variable Block
|Field          |	Description                                        |
|---------------|----------------------------------------------------|
|variable	      | Block type                                         |
|"instance_type"| Variable name                                      |
|description    | Explains the variable                              |
|type         	| Data type (string, number, bool, list, map, object)|
|default        | Optional default value                             |

## Using a Variable

```bash

resource "aws_vpc" "learning-vpc" {
    cidr_block = var.cidr_block[0]
    tags = {
        Name: "development"
        vpc_env: "dev"
    }
}
```
**var.cidr_block[0] references the variable**

There are 3 ways to pass the value to the input variable.

1. Terraform apply
 - When we use this command, it prompts to enter the value. There we have to enter the required data

2. terraform apply -var "subnet_cidr_block=10.0.30.0/24"
 - We can pass the values to a variable in command only.

3. creating a file with name terraform.tfvars
- If it is created with anothername.tfvars,we have to set a file in command, as terraform looks for terraform.tfvars file.
  ```bash
  terraform apply -var-file anothername.tfvars
  ```

<details><summary>23. count (Meta-Argument)</summary><br><b>

  count is a meta-argument used to create multiple instances of a resource using a numeric value.
  - Q1: When do you use count?
    - When I need multiple identical resources, like creating 3 EC2 instances.
  - Q2: Limitation of count?
    - If we remove one element from middle, Terraform may recreate resources because it is index-based.
      ```bash
      resource "aws_instance" "web" {
       count         = 3
       ami           = "ami-123456"
       instance_type = "t2.micro"

       tags = {
         Name = "web-${count.index}"
        }
      }

      Access Specific Instance:
      aws_instance.web[0].id
      ```
</b></details>
<details><summary>24. for_each (Better than count)</summary><br><b>
  
  - for_each is used to create multiple resources using a map or set of values. It is more stable than count because it uses keys instead of index.
  - Q1: Difference between count and for_each?
    - count uses numeric index and can cause resource recreation if order changes. for_each uses unique keys, making it safer for production.
      ```bash
      variable "instances" {
       default = {
        dev  = "t2.micro"
        prod = "t2.medium"
      }
      }

      resource "aws_instance" "web" {
      for_each      = var.instances
      ami           = "ami-123456"
      instance_type = each.value

      tags = {
        Name = each.key
       }
      }

      Access:
       aws_instance.web["dev"].id

      ```
  
</b></details>

<details><summary>26. What is Terraform Lifecycle Block?</summary><br><b>

  Lifecycle block controls how Terraform handles resource creation, update, and deletion to avoid downtime or accidental destruction.
  - 1. create_before_destroy
       - Creates new resource before deleting old one to ensure zero downtime.
       ```bash
       lifecycle {
         create_before_destroy = true
       }
       ```
    2. prevent_destroy
       - Prevents accidental deletion of critical resources like production database.
         ```bash
         lifecycle {
           prevent_destroy = true
         }
         ```
    3. ignore_changes
       - Tells Terraform to ignore changes to specific attributes, useful when external systems modify resource.
         ```bash
         lifecycle {
         ignore_changes = [tags]
         }

         Ignore specific attribute:
         ignore_changes = [ami]
         ```
    4. replace_triggered_by
       - Forces resource replacement when another resource changes.
         ```bash
         lifecycle {
           replace_triggered_by = [
           aws_security_group.sg
           ]
         }
    - Q: What happens if lifecycle create_before_destroy is not supported?
      - Some resources like unique names cannot be created before destroy due to API constraints.
    - Q: Can we use lifecycle in module?
      - Yes, lifecycle block can be defined inside resource within module.
    - Q: Real-world example of ignore_changes?
      - If autoscaling group modifies desired capacity automatically, we ignore that attribute.
        
         ```  
</b></details>

<details><summary>29. What are Locals Block?</summary><br><b>

  Locals are used to define reusable expressions or computed values within Terraform configuration to improve readability and avoid repetition.
  - Q1: Difference between variables and locals?

      ```bash
      }
      ```

<details><summary>What are Provisioners?</summary><br><b>

  Provisioners in Terraform are used to execute scripts or commands on local or remote machines after a resource is created or destroyed. However, they are considered a last resort and not recommended for production use.
  - Types of Provisioners in Terraform
  - There are 3 main types:

1️⃣ local-exec - local-exec runs commands on the machine where Terraform is executed, not on the remote resource.
- when do use use local exec?
  - When I need to trigger local scripts, update DNS, send notifications, or integrate with external systems after resource creation.
2️⃣ remote-exec - remote-exec executes commands directly on the remote resource after it is created, typically via SSH or WinRM.
- What is required for remote-exec?
  - It requires a connection block with SSH or WinRM configuration.
3️⃣ file - file provisioner is used to copy files or directories from local machine to remote machine.
- Q: When do you use file provisioner?
  - When I need to upload configuration files, scripts, or application artifacts to the server.
- Q1: Why are provisioners discouraged?
  - Provisioners break Terraform’s declarative model and idempotency. They introduce external dependencies and make infrastructure less predictable. In production, configuration management tools like Ansible or user_data scripts are preferred.
- What happens if provisioner fails?
  - Terraform marks the resource as tainted, meaning it will be recreated in the next apply.


</b></details>
<details><summary>30. What are Terraform Functions? </summary><br><b>

  - Terraform has built-in functions to manipulate strings, lists, maps, etc.
  - 1. 🔹 lookup()
        lookup function retrieves a value from a map, with an optional default if key is not found.
       ```bash
       variable "instance_types" {
        default = {
        dev  = "t2.micro"
        prod = "t2.medium"
        }
       }

       instance_type = lookup(var.instance_types, var.environment, "t2.micro")
       ```
    2. length()
       length function returns the number of elements in a list or characters in a string.
       ```bash
       variable "subnets" {
        default = ["subnet-1", "subnet-2"]
       }

       output "subnet_count" {
         value = length(var.subnets)
       }
       ```
    3. join()
       join function concatenates list elements into a single string using a separator.
       ```bash
       variable "names" {
        default = ["web", "app", "db"]
       }

       output "joined_names" {
         value = join(",", var.names)
       }
       Output: web,app,db
       ```
    4. Q: Why use functions in Terraform?
       - To make configurations dynamic, reusable, and environment-aware.

<details><summary>31. What are Terraform Triggers?</summary><br><b>

  - Triggers are mainly used in null_resource.
  - Triggers are used inside null_resource to force re-execution when specific values change.
  - Terraform normally runs provisioners only during creation.
  - Triggers allow us to rerun them when input changes.
  - Q1: When do you use triggers?
    - When I need to rerun provisioners based on changes like file hash, configuration updates, or script changes.
  - Q2: What is null_resource?
    - It is a placeholder resource used to execute provisioners without creating real infrastructure.
      ```bash
      resource "null_resource" "deploy" {
        triggers = {
          file_hash = filesha256("app.zip")
        }

       provisioner "local-exec" {
         command = "echo Deploying new version"
       }
     }
    ```

<details><summary>33. What is a null resource in Terraform?</summary><br><b>

  A null_resource in Terraform is a resource that doesn’t create any actual infrastructure, but is used to execute scripts or perform actions during the Terraform lifecycle.

  ```bash
resource "null_resource" "run_script" {
  triggers = {
    always_run = timestamp()
  }

  provisioner "local-exec" {
    command = "bash deploy.sh"
  }
}
```
Explanation:
- triggers forces Terraform to re-run the resource when values change
- timestamp() ensures it runs every time
</b></details>
<details><summary>34. What is Terraforom Taint?</summary><br><b>

  Terraform Taint is used to forcefully recreate a resource in the next terraform apply, even if there are no configuration changes.
  - We use taint when:
    - A resource is partially broken
    - Provisioning failed midway
    - Manual changes caused inconsistency
    - You want to recreate without changing code
</b></details>

<details><summary>35. What is Terraform Refresh?</summary><br><b>

  Terraform Refresh is used to update the Terraform state file with the real-time infrastructure state from the provider (like AWS), without making any changes to the actual resources.
  
  - Reads current infra (EC2, S3, etc.)
  - Compares with state file
  - Updates the state file only
  - Does NOT modify infrastructure
</b></details>

<details><summary>37. How do you detect and fix configuration drift?</summary><br><b>

  Configuration drift happens when actual infrastructure differs from Terraform code, usually due to:
  - Manual changes in cloud console
  - Scripts outside Terraform
  - Failed or partial deployments

    How do I detect drift?
    - Using terraform plan
      ```bash
      terraform plan
      ```
    - Using refresh-only mode
      ```bash
      terraform apply -refresh-only

      Updates state without changing infra
      Helps confirm drift safely
      ```
    - CI/CD Drift Detection (Real-world)
      - In production, I:
      - Run terraform plan in Jenkins pipeline daily
      - Alert if any drift is detected
      - Prevent unauthorized manual changes
</b></details>
